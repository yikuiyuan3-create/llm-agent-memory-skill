# 最小记忆约定（工程建议）

需要落地字段、冲突处理或生命周期时读取。本文件是基于综述框架的工程建议，不是论文定义的标准；复用项目已有字段即可，不要求重建数据库。

一条记忆应能回答：谁可用、依据是什么、何时有效、当前是否可用。通常保留：

| 信息 | 用途 |
|---|---|
| 稳定 ID、版本 | 幂等更新、定位派生记录 |
| 内容及类型 | 区分观察事实、用户明确偏好、待验证经验 |
| 来源引用、原始记录定位 | 核对证据；避免摘要替代原始依据 |
| 来源类别、任务/用户/租户作用域 | 决定读取权限和生命周期 |
| 观测时间、事实生效区间、最近核验时间 | 区分“刚上传”与“刚发生” |
| 状态、派生关系 | 区分有效、待验证、冲突、失效；修正传播 |

置信度只在有明确口径时增加；模型自评数字不能替代证据。日志优先记录 ID、动作、时间、版本与原因，避免复制敏感原文。

建议生命周期：候选 → 核验后可用；候选也可被拒绝。有效记录可被更正、失效或按实际授权删除。需保留的审计信息遵从既定期限，删除操作同时考虑原记录、摘要、索引与缓存。逻辑失效只是不再使用，不等于清除已存数据；以清单和实际读回/检索结果验证已授权范围，对备份等未核验副本说明处理状态，不报告无法证明的彻底清除。

冲突例子（合成数据）：今天导入的旧库存报表，与昨天从业务系统核验的当前库存冲突。应按事实对应时间和权威系统确认，不能仅按导入时间采用今天的记录。昨天核验的数据也只说明昨天状态，若询问实时库存仍须重新查询获准的业务源。若无法确认，就报告冲突，不猜一个数。

高风险问题无法通过记忆确认时，回到获准的原始来源；来源不可用就标明缺口。短期有效性不采用统一 TTL，按信息类型、更新频率与错误成本制定。
